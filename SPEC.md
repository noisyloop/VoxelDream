# VoxelDream — Claude Code Build Prompt

Paste this whole file as the opening message of a fresh Claude Code session, or drop it in the repo root as `SPEC.md` and say "read SPEC.md and build Milestone 0."

## Identity

VoxelDream is a browser-based voxel world builder that teaches computer graphics by making you earn every tool you use. It is a Metroidvania whose power-ups are creative competencies. It is also, when you close the game layer, a serious voxel editor with a real path-traced renderer and honest export targets.

It is not a MagicaVoxel clone. MagicaVoxel gives you an empty grid and a palette. VoxelDream gives you one brush at a time, in an order that builds understanding, and the sandbox unlocks as you go.

## Absolute constraints — do not violate these

1. **Zero binary assets. Ever.** No `.png`, no `.jpg`, no `.glb`, no `.wav`, no font files, no downloaded meshes, no textures. Every visual, every sound, every model in this repo is generated by code at build time or runtime. If a texture is needed, write the function that produces it. If a mesh is needed, write the generator. If a UI icon is needed, it is inline SVG authored as a path string in a `.ts` file. If a sound is needed, it is a Web Audio graph.

   This is not an aesthetic preference. It is the pedagogy. The repo is the curriculum: every asset in it is a worked example of the concept it demonstrates. A student can open any file and see how the thing was made.

2. **WebGPU is the primary target.** WGSL compute shaders own the brickmap traversal and the cellular automata step. WebGL2 exists only as a degraded fallback for the meshed preview mode — do not attempt to backport global illumination to it. Detect, warn, degrade.

3. **Three.js does not own the render loop.** It may be imported only for glTF/USDZ serialization and scene-graph interop at export time. The renderer is hand-written WGSL.

4. **No `localStorage` assumptions in shared demo builds.** Persistence is opt-in, file-based (`File System Access API` where available, download/upload fallback everywhere else).

5. **Every shader ships with its own explanation.** Each `.wgsl` file has a header comment block: what technique, what paper or reference, what the uniforms mean, what happens if you change each one. These comments are parsed at build time and surfaced in the in-app "show me the code" panel. The comments are not documentation debt — they are a product feature and a build-time dependency.

## Research phase — do this first, before writing code

Use web search and your judgment. Produce `RESEARCH.md` in the repo root summarizing findings, with links, before touching the renderer. Do not trust your priors on any of these; the field has moved.

### Rendering

* **Radiance cascades.** Find the current best public write-ups and reference implementations. Determine whether the 3D formulation is tractable for a browser brickmap or whether a probe-based / cone-traced approach (à la VXGI, or the simpler DDGI) is the pragmatic pick. Report the memory footprint per cascade at a target world size of 512³. Make a recommendation and defend it.
* **Brickmap / sparse voxel DDA traversal.** Survey current approaches: Amanatides–Woo baseline, ESVO, brickmaps with occupancy bitmasks, GPU-side hierarchical DDA. Report expected ray throughput. Identify the cheapest structure that supports live editing — many published structures assume a static scene and are useless to us.
* **Temporal accumulation + reprojection.** What is the minimum viable TAA/reprojection for a progressive path tracer that must remain interactive during camera motion. Include the standard failure modes (ghosting on edits, disocclusion) and their standard mitigations.
* **Greedy meshing for the fast "Waking" mode.** Get the canonical algorithm right, including the ambient-occlusion-at-vertices trick that makes voxel meshes look good for free.

### Formats

* **MagicaVoxel `.vox`** — full chunk-level spec, including `RGBA`, `MATL`, `nTRN`/`nGRP`/`nSHP` scene graph, and the default palette. We must import and export losslessly for the subset we support.
* **glTF 2.0 / GLB** — binary chunk layout, how to emit a palette as a small texture or as per-primitive materials, and which choice game engines actually prefer.
* **USDZ** — what the minimum viable file looks like for iOS AR Quick Look. Confirm whether it can be emitted from the browser without a native toolchain.
* **STL** — trivial, but confirm the manifold/watertight requirements for printability and what our mesher must guarantee.

### Simulation

* **Cellular automata for falling sand in 3D, GPU-side.** The classic 2D pixel-sim approaches (Noita-style) do not port cleanly because of the double-buffer race on diagonal moves. Find the standard GPU solution (margolus neighborhoods? checkerboard passes? per-brick serial passes?) and report.

### Procedural asset generation

Because we ship no binaries, catalogue the techniques we'll need and confirm the good ones:

* Value/gradient/simplex noise, fBm, domain warping, worley — WGSL implementations, hash function quality, and whether to precompute a permutation table or hash on the fly.
* Blue noise generation in-shader (or a compute-generated blue noise texture at boot) for stochastic sampling.
* Procedural text rendering without font files: SDF glyph construction from bezier path data authored as source, or an MSDF pipeline generated at build time from a code-defined typeface. Investigate both; recommend one. A code-authored geometric typeface is acceptable and probably correct for this project.
* Web Audio synthesis for UI feedback and ambience. No samples.

Stack: TypeScript, Vite, Zustand, hand-written WGSL. Vitest for logic, and a golden-image test harness for shaders (render at fixed seed, compare against a checked-in procedurally regenerable reference — store the hash, not the image).

## The two render modes

They are both real. The toggle between them is the app's identity.

* **Waking** — greedy-meshed, rasterized, vertex AO, 120fps, fully editable, instant feedback. This is where you build.
* **Dreaming** — brickmap raymarch, global illumination, volumetrics, depth of field, progressive temporal accumulation. Freezes on camera motion to a fast DDA path, converges when still. This is where you look.

Editing in Dreaming mode is allowed and must invalidate accumulation gracefully — a stamp of new voxels should reconverge in under a second, not reset the frame to noise.

## Milestone 0 — the vertical slice, and nothing else

Do not build the editor. Do not build twelve dreams. Do not build all the exporters. Build exactly this, and stop:

**Dream 01: Light.**

A dark voxel room, ~64³, generated procedurally at load. The player has exactly one tool: place a single emissive voxel. When they place it, the GI pass runs and the room blooms with bounced colour. Nothing explains normals or bounce or falloff. They just see it.

On completion: the emissive brush is unlocked into a bare sandbox (place, erase, orbit, nothing more), and one button appears — **Export as shader** — which bakes the 64³ world into a 3D texture, emits a self-contained GLSL fragment shader that raymarches it, and hands the user a `.glsl` file that runs unmodified on Shadertoy.

That is the whole milestone. It proves the renderer, the progression, and the export thesis in one ten-minute loop.

### Definition of done for Milestone 0

* [ ] `RESEARCH.md` exists, is substantive, and its recommendations were followed
* [ ] `npm run dev` opens a dark room in a browser with WebGPU
* [ ] Placing an emissive voxel produces visibly bounced indirect light — not just a point light with falloff. Turn it off in a debug flag and the difference must be obvious in a screenshot.
* [ ] Camera motion stays above 60fps at 1080p on integrated graphics; accumulation converges within ~1s of the camera stopping
* [ ] Zero binary files in `git ls-files` (add a CI check that fails the build on any file extension outside an allowlist)
* [ ] The "show me the code" panel renders the doc header from the actual GI shader, parsed at build time — not a hardcoded string
* [ ] Export button produces a `.glsl` file. Paste into Shadertoy. It renders the room. This is the acceptance test; do it manually and screenshot it.
* [ ] `npm test` green

## Working agreement

* Ship Milestone 0 completely before proposing Milestone 1. Resist scope. This spec describes three products — a renderer, an editor, and a game — and each is a year of work. The slice above is what proves all three are worth building.
* When a technique from `RESEARCH.md` turns out to be wrong in practice, update `RESEARCH.md` and say so. The research doc is a living record, not a one-time gate.
* Commit in small, reviewable units. Every shader lands with its doc header and its golden-image hash test in the same commit.
* If you find yourself about to `curl` an asset, stop. Write the generator instead.
